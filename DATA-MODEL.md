# DATA-MODEL.md — Canonical Data Reference

## Scope

**What this is:** The single source of truth for every data structure in the project — S3 object layout, JSON documents, SQLite schema, repository interfaces.

**What's in here:** Element JSON schema, project meta, SQLite tables, indexes, S3 keys, job status values.

**What's NOT here:** Page layouts (→ UI-CONCEPT.md), API endpoint definitions (→ AGENTS.md), how data moves through services (→ AGENTS.md), testing strategy (→ TESTING.md), sdcpp API shapes (→ SDCPP-API.md).

## S3 Project Layout

```
projects/
├── {name}/
│   ├── elements/
│   │   └── {uuid}.json        # Element JSON document
│   └── images/
│       └── {uuid}.png         # Generated image (PNG only)
```

**S3 is authoritative.** Every persistent piece of data lives in an S3 object. The JSON document is the single source of truth.

**SQLite is disposable — and not even a permanent architectural commitment, just what's fast and convenient right now.** It is a projection of JSON documents. It may be deleted and must be recreated automatically by scanning S3. No business logic depends on SQLite. Nothing about the design assumes SQLite specifically: if a future retrieval need genuinely outgrows it, the same "it's a disposable index over the S3 truth" philosophy applies to replacing SQLite itself, not just deleting `cache.db` — throw it away, rebuild against whatever's better, because S3/JSON is still the truth either way. Nothing like this is planned; it's a contingency for *if* real limits show up, not a direction the project is heading.

**Write direction is strict:** validate → JSON → S3 → SQLite. Direct SQLite writes are forbidden.

## Element JSON

The JSON file contains the complete generation context. This is the **master record** — everything stored in SQLite is extracted from it.

**Design philosophy, stated once here because it governs every future change to this document, not just this revision:** this JSON is not tuned for query performance — that's what the extracted SQLite columns are for. It's tuned for structure and completeness, modeled as a DDD aggregate: `Element` is the aggregate root; `Generation`, `Image`, `ElementModel`, `ElementRef` are its value objects. A future change that flattens something back out "for query convenience" is optimizing the wrong artifact — that pressure belongs on the SQLite extraction, not on this document's shape.

### Go struct (source of truth)

```go
type Element struct {
    ID            string      `json:"id"`
    Project       string      `json:"-"`                     // derived from S3 path, not persisted in JSON
    Kind          string      `json:"kind"`                  // output media type: "image" (later maybe "video") — shared vocabulary, extensions can set it too
    Origin        string      `json:"origin"`                // "generated" | "external" | "ext/{owner}/{extension}" — see note below
    SchemaVersion int         `json:"schema_version"`        // structural shape of this document — see note below
    Version       int         `json:"version"`               // regeneration count for this element ID; bumped by Regenerate, default 1
    CreatedAt     time.Time   `json:"created_at"`
    Generation    *Generation `json:"generation,omitempty"`  // present only for the core-native "generated" origin — never for "external" or any "ext/..." origin
    Image         *ImageInfo  `json:"image,omitempty"`
}
```

**`Origin` is an open namespace, not a closed two-value enum.** `"generated"` and `"external"` are core's own two values. Anything an extension originates instead uses `"ext/{owner}/{extension}"` — the same namespacing convention EXTENDING.md already uses for routes and S3 storage paths, reused here for a third purpose. **What goes where, stated plainly:** for `"ext/..."` origins, core's own Element JSON carries only identity, origin, kind, and image — no `Generation`, ever. Whatever that extension actually needs to record about how the element came to be lives entirely in the extension's own storage (Pattern A/B, per EXTENDING.md), not in core's document. `Generation` is specifically the shape for core's own sdcpp-backed generation — it's not a general "however this got made" object extensions plug into.

**`element_references` (below) stays scoped to this same boundary — worth being explicit, since it would be easy to accidentally widen it.** It backs `Generation.ReferenceImages` specifically, core's own img2img case. It is not a general "any element can record what it references" facility open to extensions — building it that way would quietly reintroduce the shared, any-extension-composable lineage graph this project already decided against elsewhere (see IDEAS.md's Element Lineage notes). An extension that needs its own "made from" fact keeps that as its own narrow record, in its own storage, same as that earlier decision already established.

**`version` vs `schema_version` — two different questions, deliberately not one field.** `Version` is domain data: how many times this exact element (same ID) has been regenerated, e.g. after a faulty backend run — driven by the existing Regenerate feature, not by this document's shape. `SchemaVersion` is purely about which structural shape the JSON is in, for future migrations — independent of how many times the underlying image was regenerated. Conflating them was the previous version of this document's mistake, worth naming as a mistake rather than quietly fixing.

**img2img fields (`Strength`, `InitImage`) are JSON-only.** They are not extracted to SQLite columns because gallery queries never filter or sort on them — they are purely payload data for the sdcpp img_gen request. This follows the general rule: don't prematurely optimize the cache layer; extract to SQLite only when there's a query need. The `strength` field defaults to 0.75 when absent; `init_image` is a base64 data URL used for the "edit this element" flow.

**No defensive legacy-shape handling in the application — a one-time transform, not a permanent compatibility path.** Nothing has shipped yet, so rather than write code that tolerates an older flat shape indefinitely, existing S3 data gets transformed once, directly, via a small `jq` script (see `migrate-elements-to-schema-v1.sh`) before any of this ships. Every element in S3 ends up genuinely at `schema_version: 1`, in the shape this document describes — the application can parse that shape directly, with no "missing field, assume legacy" branches to write, test, or explain to a future agent. If a real incompatible change is ever needed after release, it gets the same treatment then: an explicit, deliberate transform plus a `schema_version` bump, not permanent defensive parsing baked in ahead of time. `SchemaVersion` itself doesn't need a SQLite column — nothing queries or filters by it, it's consumed once at JSON-parse time and can be dropped after that.

```go
// Generation holds everything about how a generated element came to be:
// request parameters (shape depends on Task). Only present when Element.Origin == "generated".
type Generation struct {
    Task            string        `json:"task"`                          // "txt2img" | "img2img" | ... — "upscale" shown below as illustration only, not decided as core vs. extension yet
    Model           *ElementModel `json:"model,omitempty"`
    Prompt          string        `json:"prompt,omitempty"`
    NegativePrompt  string        `json:"negative_prompt,omitempty"`
    Width           int           `json:"width,omitempty"`
    Height          int           `json:"height,omitempty"`
    Seed            int64         `json:"seed,omitempty"`
    SampleSteps     int           `json:"sample_steps,omitempty"`
    TxtCfg          float64       `json:"txt_cfg,omitempty"`
    BackendRef      string        `json:"backend_ref,omitempty"`
    ReferenceImages []ElementRef  `json:"reference_images,omitempty"`    // task: img2img — ordered, maps to sdcpp's ref_images
    SourceElementID string        `json:"source_element_id,omitempty"`  // task: upscale
    UpscaleFactor   float64       `json:"upscale_factor,omitempty"`     // task: upscale
}
```

```go
// Only Architecture is required — other fields are optional and
// only relevant for certain model architectures (e.g. FLUX has
// variants and parameter counts; SD1.x only needs a name).
// The architecture field lets the system select which UI settings
// to show and which defaults make sense.
type ElementModel struct {
    Architecture string `json:"architecture"` // required — e.g. "flux2", "sd3", "sdxl"
    Variant      string `json:"variant"`      // optional — e.g. "klein", "dev"
    Params       string `json:"params"`       // optional — e.g. "9B", "1.0", "1.2"
    Quantization string `json:"quantization"` // optional — e.g. "Q4_K", "FP8", "FP16"
    Name         string `json:"name"`         // optional — full model filename
}
```

**`Generation.Model` is `*ElementModel`, a pointer, not a value.** Go's `encoding/json` `omitempty` does not omit zero-valued structs — only nil pointers, empty slices/maps, and zero primitives. A value-typed field would serialize an empty `{"architecture":""}` for any task that has no model to report, regardless of the struct tag.

```go
type ElementRef struct {
    ElementID string `json:"element_id"`
}

type ImageInfo struct {
    ProjectLocation string `json:"project_location"` // project-relative path: images/{id}.png
    Format          string `json:"format"`
    Width           int    `json:"width"`
    Height          int    `json:"height"`
    SizeBytes       int64  `json:"size_bytes"`
}
```

**No top-level shim fields exist** — all generation fields live exclusively under `generation.*` in the JSON document stored in S3. SQLite's flattened columns (`prompt`, `seed`, `width`, `height`, `sample_steps`, `txt_cfg`, `duration`) are extracted at sync time for query performance; they are a cache projection, not a structural duplicate. `Element.Generation` and `Element.Image` are reconstructed from SQLite's flattened columns at read time (`GetElement`/`ListElements` never fall back to S3 — see Read Path, below), not scanned as a single JSON blob column; `Element` also carries an internal `extFields` map for extension column values, populated the same generic way via the Query Builder's `SetField(col, value)`. Templates access extension fields via `getField` / `getFieldInt` — no extension-specific struct fields exist on core `Element`, `Generation`, or `Image`. `Generation.ReferenceImages` specifically is backed by `element_references` (below) on read, not by re-parsing S3.

**Schema history — one entry, expected to stay one entry for a while:**

| `schema_version` | Shape |
|---|---|
| `1` (current) | Everything this document describes — `origin`, nested `generation` with `task`, `element_references`. Applies to every element in S3 as of the one-time `jq` transform (`migrate-elements-to-schema-v1.sh`) — nothing older is expected to exist, and the application isn't written to tolerate anything older. |

If a genuinely incompatible change is needed after release, it gets its own transform script and its own `schema_version` bump then — this table gains a row at that point, rather than the application growing permanent defensive parsing ahead of time for a case that may never happen.

## Element Lifecycle

The element goes through distinct phases. S3 and SQLite are touched at different points:

| Phase | S3 `elements/{id}.json` | S3 `images/{id}.png` | SQLite `elements` |
|---|---|---|---|
| **1. Created (job start)** | Written by `StartJob` → `CreateElement` with minimal JSON (no `image`, `Duration = 0`) | Not written | `INSERT` row |
| **2. Polling in flight** | No writes. The element JSON sits on S3, unchanged. | No writes. | `jobs` table has a `queued`/`generating` row. |
| **3. Job completion** | Written again by `handleJobSuccess` → `CreateElement` with full JSON (`image` populated, `Generation.Duration` set) | Written by `handleJobSuccess` | `INSERT OR IGNORE` (or `UPDATE` on version mismatch). `jobs` row deleted immediately. |
| **4. Stable (post-completion)** | No further writes. The JSON on S3 is the single source of truth. | No further writes. | Synced from S3 on next startup via `SyncFromStorage`. |
| **5. Deletion** | Both objects deleted by `DeleteElement` | Both objects deleted by `DeleteElement` | `DELETE` from `elements` and `jobs` |

**Key invariant:** the element JSON is always written **before** SQLite is updated. `CreateElement` marshals the Element to JSON and puts it on S3 first; only after that succeeds does it update SQLite. The `duration` field is set on `Generation.Duration` during polling (step 3) — it is **not** available at step 1 (the element is created with `Duration = 0`), because the job hasn't finished yet.

**After step 3, the S3 object is immutable.** Nothing modifies the element JSON after a successful job completion. `Regenerate` creates a **new** element with a **new** ID (same seed, same parameters), not a mutation of the existing one. `SyncFromStorage` on startup may `UPDATE` the SQLite row with version-aware upserts, but it never mutates the S3 object.

## SQLite Schema

The real schema from `internal/data/sqlite.go`. This is the authoritative version.

```sql
CREATE TABLE IF NOT EXISTS projects (
    name          TEXT PRIMARY KEY,
    schema_version INTEGER DEFAULT 1,
    version       INTEGER DEFAULT 1,
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at    DATETIME,
    synced_at     DATETIME,
    hidden        INTEGER DEFAULT 0,
    backend_ref   TEXT DEFAULT '',
    description   TEXT DEFAULT '',
    tags          TEXT DEFAULT '[]',
    friendly_name TEXT DEFAULT '',
    primary_owner TEXT DEFAULT ''
);

CREATE TABLE IF NOT EXISTS elements (
    id               TEXT PRIMARY KEY,
    version          INTEGER DEFAULT 1,
    project          TEXT NOT NULL,
    created_at       DATETIME DEFAULT CURRENT_TIMESTAMP,
    project_location  TEXT,
    etag             TEXT,
    synced_at        DATETIME,

    -- Extracted for fast queries. model_name/prompt/seed/width/height/
    -- sample_steps/txt_cfg/duration now come from element.generation.*
    -- (was top-level before the Generation restructure) — null for any
    -- element with no Generation at all (origin = "external").
    origin           TEXT DEFAULT 'generated',
    model_name       TEXT,
    prompt           TEXT,
    seed             INTEGER,
    width            INTEGER,
    height           INTEGER,
    sample_steps     INTEGER,
    txt_cfg          REAL,
    duration         REAL,

    FOREIGN KEY (project) REFERENCES projects(name)
);

CREATE INDEX IF NOT EXISTS idx_elements_project ON elements(project);
CREATE INDEX IF NOT EXISTS idx_elements_project_created ON elements(project, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_elements_model ON elements(model_name);
CREATE INDEX IF NOT EXISTS idx_elements_seed ON elements(seed);
CREATE INDEX IF NOT EXISTS idx_elements_origin ON elements(project, origin);

-- Ordered reference-image list per element, projected from the element's
-- own "generation.reference_images" JSON array for querying/navigation. Core, not an
-- extension — every generated or external element can participate.
-- ref_element_id intentionally has no FK constraint: S3 listing order is
-- arbitrary during sync (the element it points to might come later or might
-- not exist at all), and a referenced element may be deleted between sync
-- runs. Without the FK, sync is a single pass and orphaned refs are safe —
-- the JOIN query silently skips missing elements.
CREATE TABLE IF NOT EXISTS element_references (
    element_id     TEXT NOT NULL,   -- the element that HAS references
    position       INTEGER NOT NULL,
    ref_element_id TEXT NOT NULL,   -- the element being referenced (no FK)
    PRIMARY KEY (element_id, position),
    FOREIGN KEY (element_id) REFERENCES elements(id) ON DELETE CASCADE
    -- ref_element_id intentionally has no FK constraint: S3 object listing
    -- order is arbitrary, and a referenced element may be deleted between
    -- sync runs. Without the FK, sync is a single pass and orphans are safe.
    -- The element_id FK retains ON DELETE CASCADE so deleting an element
    -- still cleans up its own reference rows.
);

-- Forward direction ("this element's references, in order") is already
-- served by the primary key. This index is for the reverse direction —
-- "what else used this element as a reference" — the actual navigation case.
CREATE INDEX IF NOT EXISTS idx_element_references_ref ON element_references(ref_element_id);

CREATE TABLE IF NOT EXISTS jobs (
    id              TEXT PRIMARY KEY,
    element_id      TEXT,
    project         TEXT NOT NULL,
    sdcpp_job_id    TEXT,
    status          TEXT DEFAULT 'queued',
    error_msg       TEXT,
    sdcpp_started   DATETIME,
    sdcpp_completed DATETIME,
    FOREIGN KEY (project) REFERENCES projects(name)
    -- element_id FK intentionally omitted: jobs are created before elements
    -- in StartJob (CreateJob → submitJob → CreateElement), so the FK would
    -- fail because elements(id) doesn't exist yet. The relationship is
    -- maintained at the application layer: each job has a unique id (UUID)
    -- and an element_id pointing to the element it generates.
);

CREATE INDEX IF NOT EXISTS idx_jobs_element ON jobs(element_id);
CREATE INDEX IF NOT EXISTS idx_jobs_project ON jobs(project);
CREATE INDEX IF NOT EXISTS idx_jobs_status ON jobs(status);

-- App-wide settings (key-value store).
CREATE TABLE IF NOT EXISTS app_settings (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
```

**Extension columns** are not shown here. Extensions add columns via their `Migrate` method — prefixed `ext_{owner}_{extension}_{name}` — and store authoritative data in S3 delta files. The DB column is a cache; `Sync` populates it from S3 on startup. Extensions also register their columns with the Query Builder so they appear in `ListElements` scans.

## Sync Logic

### Startup sync (S3 → SQLite)

`SyncFromStorage` scans all element JSON files under `projects/{name}/elements/` and writes them to SQLite. It uses **version-aware upsert** to avoid `INSERT OR REPLACE` (which in SQLite = `DELETE` + `INSERT`, and would fire `ON DELETE CASCADE` on extension tables).

**Algorithm per element:**
1. Read element JSON from S3, extract `version` field
2. If `version` is 0 or missing (legacy JSON), treat as version 1
3. `INSERT OR IGNORE` — inserts only if the element ID doesn't already exist
4. `UPDATE ... WHERE version != ?` — updates only if the S3 version differs from the cached version

**Result:**
- New elements: inserted with version from S3
- Unchanged elements: skipped (no DELETE, no cascade)
- Modified elements: updated with new version from S3

### Reference sync (`element_references`)

Projected from each generated element's `generation.reference_images` JSON array (task: img2img) — there is no separate S3 object for it, so it rides along with the same per-element sync pass above, not a second scan. Elements with no `Generation` at all (origin: external) simply have nothing to project here.

**No FK on `ref_element_id`.** The table has a `FOREIGN KEY (element_id)` with `ON DELETE CASCADE` (so deleting an element cleans up its own reference rows), but `ref_element_id` intentionally has no FK constraint. S3 listing order during sync is arbitrary — the element being referenced might come later in the listing, or might have been deleted at S3 level between sync runs. Without the FK, sync is a single pass with no ordering requirement. Orphaned `ref_element_id` values are harmless: the JOIN query on `element_references` silently skips missing elements.

**Algorithm, keyed off the same insert-vs-update branch:**
1. **New element** (the `INSERT OR IGNORE` above actually inserted a row): insert one `element_references` row per entry in `reference_images`, in array order.
2. **Modified element** (the `UPDATE ... WHERE version != ?` above actually updated a row): `DELETE FROM element_references WHERE element_id = ?` (scoped to this one element, not a whole-table or whole-row delete — does not touch the `elements` row itself, so it does not risk the CASCADE hazard the version-aware upsert exists to avoid), then reinsert from the current JSON. In practice this branch should rarely fire — elements are treated as immutable generation records elsewhere in this project, so `reference_images` isn't expected to change after creation — but the sync has to be correct for the case where it does.
3. **Unchanged element:** skipped, same as above — no work needed.

**Orphan cleanup gap, worth flagging rather than assuming it's handled:** if an element is removed directly at the S3 level (not through `DeleteElement`), no SQL `DELETE` fires on its `elements` row either, so nothing here — or in the existing `elements` sync — currently detects or cleans that up. `element_references` inherits the same gap that extension tables already have a documented answer for (their own `Sync()` orphan pass); core doesn't yet have an equivalent pass for its own tables. Not a new problem introduced by this change, but it's the second table now exposed to it — worth deciding whether core gets an orphan-cleanup pass of its own at some point.

The lack of FK on `ref_element_id` means orphans are structurally impossible to detect at the database level — there's no `ON DELETE` cascade to fire, no constraint violation to catch. The JOIN query silently returns nothing for missing elements, which is the intended behavior but also means a stale `element_references` row can linger until the next full sync. That's fine: the cache is explicitly disposable.

**Calibration note:** the cache is explicitly disposable and not precious — a stale or slightly-wrong `element_references` row is a non-event, fixed by the next full resync. The one piece of rigor above worth keeping regardless is the CASCADE safety (never `DELETE`/`INSERT OR REPLACE` the `elements` row itself during a routine sync) — that's not about `element_references` being correct, it's about not accidentally wiping out unrelated extension data that happens to be CASCADE-linked to the same `elements` row.

### Version lifecycle

| Event | Version action |
|---|---|
| Element created in S3 | Set to 1 |
| Element modified in S3 | Increment (or reset) |
| `CreateElement` | Set `elem.Version = 1` |
| `SyncFromStorage` | Uses S3 version for comparison |
| Legacy JSON (no version) | Treated as version 1 for compatibility |

### Extension cascade safety

With version-aware sync, `ON DELETE CASCADE` on extension tables — and now `element_references`, which isn't an extension table but has the identical hazard, being CASCADE-linked off `elements(id)` — is safe:
- **Normal restart:** no DELETE fires → extension data (and reference rows) preserved
- **CASCADE fires only on:** explicit `DeleteElement` or `DeleteProject` (user-initiated)
- **Extension `Sync()` method:** still runs to clean up orphans from S3-level deletions (not covered by CASCADE); `element_references` needs the equivalent, see the orphan-cleanup note above

## Runtime Model

The following tables hold **temporary, cache-only state** — they have **no S3 backing**, are **not synced on startup**, and are **not part of the "SQLite is disposable, rebuildable from S3" guarantee**. They exist purely to answer queries efficiently during application runtime. If `cache.db` is deleted, these tables are rebuilt from their S3-backed source (or pruned for jobs) on the next startup.

### `jobs` table

Holds one row per in-flight job, keyed by `id` (PK, equals `element_id`). Rows are **deleted immediately** when a job reaches a terminal status (`completed`, `failed`, `cancelled`):

| Column | Type | Notes |
|---|---|---|
| `id` | `TEXT PRIMARY KEY` | Element this job is for (PK = element_id) |
| `element_id` | `TEXT` | Same as `id` (redundant but kept for clarity) |
| `project` | `TEXT` | Project name |
| `sdcpp_job_id` | `TEXT` | Remote sdcpp job ID (for cancellation / recovery) |
| `status` | `TEXT` | `"queued"` / `"generating"` / `"completed"` / `"failed"` / `"cancelled"` |
| `submitted_at` | `DATETIME` | When job was submitted (not in actual schema; use `sdcpp_started` for start time) |
| `updated_at` | `DATETIME` | Last status update (not in actual schema; use `sdcpp_completed` for completion time) |
| `error_msg` | `TEXT` | Failure reason |

**Note:** The actual SQLite schema uses `sdcpp_started` and `sdcpp_completed` instead of `submitted_at` and `updated_at`. The `sdcpp_started` column tracks when the job was submitted to sdcpp (equivalent to submitted_at), and `sdcpp_completed` tracks when the job finished. The `submitted_at` and `updated_at` columns in the Runtime Model summary are approximate — the real schema has `sdcpp_started` and `sdcpp_completed` which serve the same purpose.

**Lifecycle:** created at job start, pruned at job completion. The `jobs` table is **not** a historical log — it tracks only "Active Jobs." Historical job context is captured in `element.generation` (the element JSON), not in a separate job record.

**Recovery:** on startup, `CancelStuckJobs` scans the `jobs` table for any rows with `status IN ('queued', 'generating')` and cancels them (sends POST to sdcpp if `sdcpp_job_id` is set). If `cache.db` is deleted, these rows are gone — but that is correct, because the stale jobs should be cancelled anyway.

### `element_references` table

Projects each generated element's `generation.reference_images` JSON array into a relational format for "what elements reference this one" queries. One row per reference entry:

| Column | Type | Notes |
|---|---|---|
| `element_id` | `TEXT` | The child element (the one that references) |
| `ref_element_id` | `TEXT` | The parent element being referenced (same name as in schema: `ref_element_id`) |
| `position` | `INTEGER` | Position in `reference_images` array (same name as in schema: `position`) |

**Synced from:** `generation.reference_images` (stored in S3 element JSON) during `SyncFromStorage`. This is the **only** source — there is no separate S3 object for `element_references`. The table is **rebuilt** (not incrementally updated) on every sync: existing rows for an element are deleted and replaced with the current `reference_images` entries from its JSON.

**Disposability:** if this table is deleted, it is rebuilt from S3 on the next startup. It is **not** S3-backed itself — it is a projection of data already stored in element JSON.

### Summary: what is persistent vs runtime

| Data | S3 | SQLite | Notes |
|---|---|---|---|
| Element metadata + params | ✅ | ✅ (cache) | Element JSON is authoritative |
| Element image | ✅ | — | PNG stored in S3 |
| Job in-flight status | — | ✅ (runtime) | Pruned on completion |
| Reference relationships | — | ✅ (cache) | Projected from element JSON |
| Projects | — | ✅ (cache) | Discovered from element JSON on sync |

## Contracts — Shared Behavioral Interfaces

Contracts are small capability interfaces that let extensions share a common language for reading and recording sequences of actions — **traits in Go's style**, not structs. Each extension satisfies the interfaces via its own types and thin accessor methods, keeping its own storage and orchestration entirely unchanged.

### Package

`internal/contracts/contracts.go`

### ElementRef

Points to the Element a step produced, if any. Always singular — one Step produces at most one Element. A batch producing N elements has N Steps (one per item), each with its own singular output.

```go
type ElementRef struct {
    ElementID string `json:"element_id"`
}
```

### Step

The minimal shared contract for one tracked unit of work.

```go
type Step interface {
    Type() string          // extension-defined, e.g. "photobooth.capture", "batch.item"
    Status() string        // exact, extension-specific status
    CanonicalStatus() string // coarse-grained canonical state
    Output() *ElementRef   // the Element this step produced, if any
}
```

**`CanonicalStatus`** — optional in the sense that extensions that don't need a generic view may return their exact `Status()` as-is. Extensions that do canonicalize return one of five well-known states:

| Canonical state | Maps from (examples) | Dashboard treatment |
|---|---|---|
| `"running"` | `generating`, `processing`, ... | Spinner / progress |
| `"success"` | `completed`, `done`, ... | Green checkmark |
| `"failed"` | `timeout`, `wrong format`, `limit reached`, `internal error`, ... | Red + retry affordance |
| `"cancelled"` | User/system cancellation | Dim / label |
| `"waiting"` | `pending`, `enqueued`, `waiting for resources`, ... | Clock / queued indicator |

The abstraction is lossy only on sub-reasons: `timeout`, `wrong format`, and `limit reached` all map to `"failed"`, but `"failed"` stays distinct from `"cancelled"` and `"success"`. Generic code checks with a type assertion:

```go
if cs, ok := step.(interface{ CanonicalStatus() string }); ok {
    state := cs.CanonicalStatus() // one of the five canonical states above
}
```

**Adopters:**
- `SimpleStep` — no-frills struct with `CanonicalStatus_` field. When empty, `CanonicalStatus()` returns `Status_` as-is.
- `BatchItem` — satisfies via `Type()`, `Status()`, `CanonicalStatus()`, `Output()` accessor methods; maps `pending→waiting`, `generating→running`, `completed→success`, `failed→failed`, `cancelled→cancelled`.

### Card

The minimal contract for an ordered sequence of Steps.

```go
type Card interface {
    ID() string      // card's unique identifier
    Project() string // project this card belongs to
    Steps() []Step   // ordered list of steps
}
```

**Optional derived state:** `SimpleCard` derives its own `CanonicalStatus()` from its Steps — `"running"` if any Step is `"running"`; otherwise iterates in reverse to find the most specific terminal state (`"failed"` > `"cancelled"` > `"success"`). An empty card defaults to `"success"`.

**Adopters:**
- `SimpleCard` — no-frills struct with derived `CanonicalStatus()`. Fields: `ID_`, `Project_`, `CreatedAt`, `Steps_`.
- `Batch` — satisfies via `ID()`, `Project()`, `Steps()` accessor methods; keeps its own SQLite storage and orchestration unchanged.

### Job

An empty marker type. Zero fields, zero methods, no interface participation. Its sole purpose is documentation: embedding it in a concrete job type signals which package a Job belongs to, and makes the embedding pattern obvious to readers.

```go
type GenerationJob struct {
    Job
    Prompt    string
    ModelName string
    // ...
}
```

This is the **Transition** side of a Petri net — active, not passive. Transitions don't hold state; they *fire*, deposit a **Token** (Element) into a **Place** (Step), and move on. A marker type is all they need.

### Storage Model

Each extension stores its own Card+Step records in its own S3/SQLite storage — the same precedent Batch's position/status columns established. Core defines the interfaces; core does not define a table for Cards, does not provide a way to register step handlers, does not dispatch anything or decide which steps run or in what order. This is not a wiring mechanism. Step and Card only give whoever is orchestrating a common place to write down what happened.

### Design Rationale

A shared shape is not the same risk as a shared wiring mechanism. Card/Step's shared recording shape (both above) sounds like the same kind of thing as the rejected shared lineage graph — both are "core infrastructure multiple extensions touch." They aren't the same risk: a wiring mechanism *decides* what feeds what, dynamically, across arbitrary extensions — that's the composability the product vision rules out. A shared shape for *recording* a value someone else already decided to produce doesn't decide anything; it's closer to a shared vocabulary than a shared engine.

The tell, worth checking any future "should this be a shared core thing" question against: does adopting it let two extensions compose in ways neither author anticipated? If yes, it's the graph. If it just gives them a common place to write down what already happened, it's Card/Step. Card/Step's resolution (above) has a concrete mechanism for staying on the right side of this line: a small interface (Go's trait) rather than a shared struct — a type can *behave* like a Step without being forced to *become* one, storage and orchestration untouched.

**Batch and Photobooth satisfy the same trait in structurally different ways:** Batch is *homogeneous* repeated steps — the same `Type()` value, N times, only the output Element differs per item. Photobooth is *heterogeneous* sequential steps — different `Type()` values, in a specific order, using `SimpleStep` directly since it has nothing extra to say. A trait that only worked cleanly for one of those would be a sign it was overfit to whichever case inspired it. Handling both without strain — one by direct use, one by thin adaptation over an untouched existing type — is a concrete signal the trait itself is right.

## Sync on Startup

1. Scan S3 for all `/elements/{id}.json` objects
2. For each element JSON: parse it, `INSERT OR IGNORE` its project row (version 1), then **version-aware upsert** the element (`INSERT OR IGNORE` + `UPDATE ... WHERE version != ?`), then sync `element_references` from the same JSON's `generation.reference_images` array (see Reference sync, above)
3. Projects are inferred from element data — no `meta.json` required
4. Run extension `Sync()` methods to clean up orphans from S3-level deletions

The sync is idempotent and self-healing. SQLite is fully rebuilt from S3 on every startup — **except `jobs`**, which is runtime-only by design and starts empty on every rebuild (see Runtime Model, above).

## Read / Write Paths

### Write Path

```
Validate → Marshal JSON → PutObject(S3: elements/{id}.json)
                        → PutObject(S3: images/{id}.png)
                        → INSERT/UPDATE SQLite
```

### Read Path

```
ListElements → Query SQLite (fast, indexed)
GetElement   → Query SQLite (no S3 fallback — DB is fully rebuilt on startup)
```

### Rules

| Rule | Enforcement |
|---|---|
| Reads prefer SQLite | ListElements, ListJobs query SQLite |
| Writes go to S3 first | CreateElement writes JSON + image to S3 |
| SQLite updated after S3 | After S3 put succeeds, update SQLite |
| No direct SQLite writes | Never INSERT/UPDATE without S3 first |
| `generation.reference_images` written once, at creation | Part of the element's own S3 JSON in the same `CreateElement` write — not a separate write path |
| sdcpp_job_id persisted | UpdateSDCPPJobID called after submitJob returns |
| Stuck jobs cleaned on startup | CancelStuckJobs called for each project at startup |
| Terminal jobs pruned, not retained | See Runtime Model, above — `jobs` rows deleted once their data has nowhere further to go |
